# 移动端四列网格 UI 审核计划

日期：2026-11-04。基线：当前 0.1.11 代码与已有 Android/Web 截图。

此文件保留 2026-11-04 的审核计划与初步判断。用户随后已授权实施；2026-11-05 的代码改动、实测结果和已知边界见[四列网格 UI 优化结果](四列网格UI优化结果.md)，长期规范见[DESIGN.md](../DESIGN.md)。

## 1. 审核依据与结论边界

以用户所指《平面中的网格设计》的网格思想为设计参照：建立稳定的边界、栏宽、栏间距、对齐关系、文字节奏与信息层级。本次未取得该书指定版本或原文，不将下列项目参数冒充书中的强制标准，不做书籍认证式的“合格”判定。

“纵向四条线”暂按移动端常用的“四列纵向网格”理解：可用宽度分为四列，页面模块按 1、2、3、4 列跨度组织。四列与四条辅助线并不等同；正式执行前应冻结一张标有左右边界、四列及三个栏间距的基准图。若用户实际指四条指定位置的辅助线，先修订基准坐标，再做后续测量。

初步判断：**现有 UI 部分具备网格基础，尚无证据证明全局满足统一四列网格。** 功能验证通过不等于布局审核通过。

已有基础：共享样式与卡片、统一主题和图标、顶部安全区、记账类别四列两行、计算器四列、单行省略、主要入口前置。

主要缺口：缺少显式网格参数与跨度约定；多个页面使用独立边距；不同弹窗与列表内部对齐尚未统一测量；小屏、字体放大和键盘状态下的节奏与触控面积需专项审核。

## 2. 建议冻结的项目网格

实施时已冻结为四列、左右 16dp、栏间距 8dp。下表保留计划参数，实际完成范围以优化结果为准。

| 参数 | 建议值/规则 |
| --- | --- |
| 单位 | React Native 布局 dp；文字按系统缩放；截图 px 必须换算 |
| 页面方向 | 本期以手机竖屏为主，横屏单独验证 |
| 列数 | 4 列 |
| 页面左右边距 M | 16dp；如保留现有 24dp，应全局选定一种，不能无理由混用 |
| 栏间距 G | 8dp |
| 列宽 C | `(W − 2M − 3G) / 4`；W 为扣除左右系统安全区后的容器宽度 |
| 跨列宽度 | `kC + (k−1)G`，k=1、2、3、4 |
| 垂直节奏 | 以 4dp 为基础，常用 8、12、16、24、32dp；字号按文字层级定义 |
| 卡片内部 | 建议统一 16dp 内边距；内容使用独立但明确的局部对齐线 |
| 触控面积 | Android 有效热区至少 48×48dp；可见图标不必放大至 48dp |
| 系统安全区 | 系统 inset 与设计留白分开计算，避免重复叠加或被覆盖 |

示例：

| 有效宽度 W | 左右边距 | 栏间距 | 单列宽 | 两列宽 | 通栏宽 |
| --- | --- | --- | --- | --- | --- |
| 320dp | 16dp | 8dp | 66dp | 140dp | 288dp |
| 360dp | 16dp | 8dp | 76dp | 160dp | 328dp |
| 390dp | 16dp | 8dp | 83.5dp | 175dp | 358dp |
| 412dp | 16dp | 8dp | 89dp | 186dp | 380dp |

列宽出现小数正常，渲染时允许设备像素取整。不要为得到整数列宽硬改内容宽度。

页面主卡片、列表、图表通常跨四列；双指标可各跨两列。组件内部的图标、标签、金额应按功能建立局部网格，不要求每个文字起点都落在页面四列的边缘上。

例外登记：日历按七天布局；底栏保留当前五个操作位置；图表按坐标和图例布局；图标库可使用独立密度网格。例外必须具有稳定边界、明确用途且可用，不因列数不同直接判失败。

## 3. 已发现的待核实事项

| 编号 | 代码/截图证据 | 初步判断 | 审核动作 |
| --- | --- | --- | --- |
| G01 | `ui.tsx` 中 header/content 为 24dp；RecordComposer header 为 12dp、类别区 18dp、计算器 14dp | 缺少统一页面边界约定 | 分别量外容器、可见图标及触控热区，确认哪些差异合理 |
| G02 | CategoryPager 使用 25% 单元格，四列两行；无显式栏间距 | 四列基础存在，尚不能等同全局网格 | 测量单元格中心、文本框、左右边界与计算器列线 |
| G03 | RecordComposer 的 keyCell 为 22% 加 flexGrow，keypad gap 为 8dp | 四列通过弹性布局实现 | 核查各宽度和缩放下四列等宽、行间对应及最后一列边缘 |
| G04 | CategoryManager 图标库每格 20%，为五列 | 属于局部网格候选例外 | 核查小屏文本、有效热区和选择状态，不直接判为四列违规 |
| G05 | 通用弹窗外边距 16dp、表单内边距 24dp；日期面板内边距 20dp | 不同容器可有差异，但缺少规则 | 为全屏页、居中弹窗、底部面板分别登记边界规则 |
| G06 | 共享 iconButton 可见/布局区域为 40×40dp；类别翻页按钮为 40×28dp | 部分触控面积可能不足 | 计入 hitSlop 后实测；不得以截图视觉大小代替有效热区 |
| G07 | 首页大入口与多层顶部信息；类别卡片纵向信息较多 | 主次明确，首屏密度仍需评估 | 测量主入口、首条数据在小屏的可见程度及信息重复 |
| G08 | 已有安全区 Provider、SafeAreaView 与额外顶部留白 | 已有修复基础 | 核查刘海/挖孔/手势导航/弹窗及系统键盘，不能只看单一截图 |

上述仅为初查，不提前给全部页面打分。旧版截图只用于理解交互，正式审核必须重新采集当前版本。

## 4. 页面审核范围

| 范围 | 网格与视觉重点 | 功能与状态重点 |
| --- | --- | --- |
| 登录、注册、模块首页 | 表单边界、主按钮、模块卡片跨度 | 键盘、错误、加载、笔记待开发状态 |
| 账本管理首页 | 顶栏、面包屑、标题、大入口、汇总的边界 | 每次进入首页、返回关系、首屏主入口 |
| 收支明细 | 筛选、视图切换、流水日期组、金额列 | 全量记录、日期升序、记录编辑、月度预算入口 |
| 类别额度与类别历史 | 图标/名称/进度/金额局部对齐 | 当前账本隔离、单类历史、收入无额度 |
| 月度预算与工资分配 | 通栏列表、固定汇总、金额与模式输入 | 全类别管理与单类编辑的边界，独立额度 |
| 记一笔与明细编辑 | 类别四列两行、备注金额区、计算器四列 | 键盘显隐、备注可见、切换类别和账本 |
| 类别管理与图标选择 | 行对齐、图标密度、长名称、省略 | 自定义名称、重复绑定、批量创建、类别额度 |
| 存款计划与详情 | 计划卡片、进度、金额、操作层级 | 存入取出、已删除计划的 App/Web 差异 |
| 统计 | 图表边界、图例、数字排版 | 空值、长类别名、极值、周期切换 |
| 我的与管理员页 | 设置行、主题选项、表单密度 | 多主题、超长账号、权限相关状态 |
| 抽屉、面包屑、日期、账本选择、确认弹窗 | 各容器边界、安全区、关闭/返回热区 | 返回上一级、内容滚动、固定操作与遮挡 |

## 5. 执行步骤与交付物

### 阶段一：建立基线

1. 冻结四列定义、边距、栏间距、文字层级及例外规则。
2. 建立“页面—共享组件—局部组件—状态”清单，区分全局问题和单页面问题。
3. 用隔离测试数据准备空账本、普通账本、工资模板、超支、无额度、长名称、长备注和 200 条以上流水。
4. 标记当前版本、平台、有效 dp、设备密度、字体缩放、安全区和输入法配置。

交付：网格参数表、页面与组件清单、状态与设备矩阵。

### 阶段二：截图叠线与测量

1. 对当前版本采集无键盘、键盘弹出、键盘收起三类截图。
2. 在截图上叠加页面四列、栏间距、外边界；卡片内另标局部起始线。
3. 测量标题、卡片、列表、筛选器、主要按钮、金额列的坐标与跨度。
4. 标注偏移值；不能把触控容器边界与可见图标轮廓混为一谈。
5. 同一共享组件在不同入口并排对比，检查状态和视觉一致性。

交付：带网格截图、测量表、截图证据路径。

### 阶段三：交互与信息层级审核

1. 核查首屏能否识别核心任务，主要操作是否唯一且突出，避免所有卡片都做成同等大入口。
2. 检查相关信息靠近、不同层级有稳定间距；收入、支出、剩余、超支不只用颜色区分。
3. 验证父级负责浏览、对象卡片承载子操作，单类别入口不打开整份配置。
4. 核对路由返回、账本切换、保存刷新和弹窗关闭是否符合页面从属关系。
5. 检查长内容、金额、大字体、键盘和安全区域是否遮挡输入及提交操作。

交付：任务路径检查表、问题清单与优先级。

### 阶段四：给出结论与改版顺序

1. 为每个页面给出“通过 / 有条件通过 / 不通过 / 待验证”。
2. 问题按共享组件归因，避免逐页做重复修复。
3. 给出首页、明细、记一笔、月度预算四个核心页面的标注方案。
4. 先处理安全区、遮挡、触控和主流程，再统一外边距与局部网格，最后调整字距、圆角等细节。
5. 审核结论和改版建议完成后再进入代码实施；本计划本身不授权发布或数据清理。

交付：审核报告、优先级清单、网格标注方案、后续实施任务表。

## 6. 验证矩阵与验收门槛

设备宽度至少覆盖 320、360、390/393、412dp；320dp 作为紧凑压力测试。主要验证 Android 原生，Web 手机视口做补充，不以 Web 替代 APK 结果。至少包括一台小屏模拟器和一台可用真机，真机结果单独记录。

字体缩放覆盖 100%、130%、最大支持字号；高字号允许合理增加行高或改为纵向排布。覆盖手势导航、底部导航栏及可用的挖孔/刘海配置。横屏、平板记录独立适配结论，不套用竖屏四列参数。

| 审核项 | 验收条件 |
| --- | --- |
| 全局网格 | 核心容器符合冻结的边界和跨度规则，所有例外有说明 |
| 对齐偏差 | 相同基准的目标偏差不超过 1dp；允许设备像素取整，文字按文字框/基线测量 |
| 垂直节奏 | 主要间距来自统一尺度；非尺度值必须有用途说明 |
| 输入与内容 | 无意外页面横向溢出，无关键金额/备注/按钮遮挡；类别分页等预期横滑除外 |
| 字体与长名称 | 默认模板类别不超过 5 字；用户名称单行省略但编辑时可见全文；大字体不遮挡主操作 |
| 触控 | 核心操作有效热区至少 48×48dp，相邻热区不重叠产生误触 |
| 可读性 | 正文对比度目标至少 4.5:1，大字及关键非文字控件至少 3:1；逐个主题实测 |
| 主次操作 | 核心任务清晰，子操作依附对象，返回和关闭含义稳定 |
| 共用组件 | 记一笔/明细编辑/管理中的同一类别和额度展示沿用同一规则与状态 |
| 系统区域 | 顶底安全区、键盘、弹窗无覆盖或重复留白问题 |

验收不以总分掩盖严重问题：核心路径只要存在安全区遮挡、无法提交、误触、错误编辑范围等问题，就不通过该轮审核。

## 7. 问题分级与记录模板

- P0：无法输入/保存、关键操作被遮挡、对象错误导致误操作，优先修复。
- P1：核心页面网格系统性不一致、主次难辨、有效热区不足、大字体严重溢出。
- P2：局部节奏、次要文字或图标对齐、非核心页面密度问题。

每条问题记录：编号、页面/共享组件、版本、设备与 dp、字体缩放、状态、实际坐标、目标值、偏差、截图、复现步骤、用户影响、优先级、建议、复验结果。
