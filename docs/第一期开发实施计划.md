### 1.2 一期交付闭环

首页选择账本 → 创建空白账本或主动选择模板 → 自定义分组/分类/tag/字段/关系 → 手动记收支 → 查看完整路径 → 工资预算显示消费后余额 → 超支提示 → 点击负tag从其他正tag扣额补足 → 同树/同层级/同标签查看 → 图表下钻 → Excel导出 → 备份并在干净安装中恢复。

以上流程须能通过签名APK连接服务器完成。飞行模式仅验证草稿保留、缓存标识和未提交状态，不宣称全功能离线。笔记入口始终静态禁用，不参与一期完成条件。

## 三、页面与交互实施清单

### 3.1 统一布局

- 根布局持有抽屉、页面标题、当前账本/月份上下文与全局错误反馈；抽屉打开能力不分散到每个页面各自实现。
- 模块首页有两张卡片：账本管理可进入，笔记管理灰色禁用；抽屉内笔记项同样禁用，没有可被深链进入的笔记路由。
- 全局账本/树范围和统计筛选分开管理，不能切换账本后仍无提示显示上个账本的数据。
- 表单支持草稿。点击抽屉按钮不提交正式流水；选择跳转前保存草稿，返回可继续。
- 数据替换等临界步骤可暂缓跳转并解释忙碌原因，普通表单不能以此为由缺失抽屉入口。

### 3.3 负tag扣额交互细节

1. 保存超支流水成功后刷新余额，提示“交通已超支100元”，提供“稍后处理”和“选择其他tag扣除”。保存成功与超支警告分别表达。
2. 点负tag进入详情，默认显示当期缺口、原始额度、消费明细、历史调入调出。
3. 展示同账本同期可用来源；默认均不勾选。来源列表同时显示余额和它是消费预算还是未实际存入的储蓄预算。
4. 用户填写每个来源扣额，预览“来源500→400、交通−100→0”；可填部分金额保留缺口。
5. 确认时重新查询余额与修订；过期预览不能直接提交。余额变化后刷新预览，让用户重新确认。
6. 成功后双方详情和预算总览同步更新，生成一组扣额记录；失败不扣任何一个来源。
7. 没有正余额时显示原因，保留负数与原始账单，不提供虚假的“一键清零”。

## 四、明确三套金额及其一致性

### 4.1 事实、预算、余额

| 数据 | 来源 | 可改变它的操作 |
| --- | --- | --- |
| 实际收支 | 用户手动账单、明确的退款/来源关联 | 新增、编辑、删除、恢复、确认计划 |
| 初始分配 | 用户工资与金额/比例规则的生效修订 | 用户明确修改预算规则 |
| tag扣额 | 用户确认的来源/目标/金额及反向撤销记录 | 确认补足或明确撤销 |
| 当前余额 | 初始分配+转入−转出−实际净使用 | 由上述事实重算，不直接手改最终数字 |

设工资总池为S、各互斥预算桶初始额度为B、使用为U、转入为I、转出为O，未分配为N：

```text
每桶余额 = B + I − O − U
ΣB + N = S
ΣI = ΣO
总剩余 = Σ每桶余额 + N = S − ΣU
```

同一时期的使用口径相同、没有新增真实使用时，扣额前后总剩余必须相同。父级汇总与子桶不同时参加Σ求和。

### 4.2 实际使用如何对应预算

- 明细唯一主分类决定消费归属；预算覆盖该分类子树，使用记录分配到其唯一互斥预算桶，辅助标签不参与扣额。
- 父项预算中细分子项时，从父项切出独立子桶，父项的直属明细与尚未细分分类落到“本级未细分”桶。各桶覆盖不重叠，父项只是汇总。
- 没有任何适用预算的分类，显示“未设置预算消费”及其实际金额，不假设0额度或强制报超支。预算总览的“全部消费”同时包含此项；预算tag余额仅覆盖已纳入的桶，另列未纳入使用，不能伪称全账本可支配余额。
- 工资模板全部消费分类配置完成后可形成完整工资池闭环；新增分类时提示纳入哪个桶或为其分配额度。
- 每个消费记录的预算投影按交易ID、预算期、互斥桶定位，交易改金额、分类、月份或删除恢复时同步重算，不能重复扣。
- 若存钱明细明确使用某工资预算的储蓄桶，其存入也占用对应额度，但不进入消费支出；没有这种关联的独立存钱记录不扣工资池。
- 同一存钱明细对同一工资方案最多一个预算占用关联，累计关联额度不得超过该明细金额；已存入不能再作为空闲额度供其他tag扣。
- 实际发生日期决定消费所属预算月份；扣额期属于预算月份，不按用户点按钮当天改变。已过月份允许手动修订，历史记录仍保留，不自动滚存。

### 4.3 改账、退款、撤销及移动

| 操作 | 实施规则 |
| --- | --- |
| 修改已补足的消费 | 重算余额，原扣额保留；原目标可能出现正余额或再次负数，用户再决定是否撤销/补足 |
| 删或恢复消费 | 同步更新预算占用与计划/存钱关联，操作历史不删除，不能为了预算平衡保留虚假流水 |
| 改分类或跨月份 | 预览旧桶释放与新桶占用；有相关预算记录时保持显式映射，不默默迁移扣额历史 |
| 改工资/分配额度 | 新建预算修订，保留消费和扣额；允许新余额为负并提示，不通过隐藏消费凑余额 |
| 撤销扣额 | 追加反向事件，不改原事件；如使原目标再为负须提示确认，不能重复撤销同一份金额 |
| 删除有关联的预算tag | 必须先处理其预算值、使用映射与扣额引用，可归档保留历史，不留下无目标事件 |
| 移动有预算绑定的分类子树 | 先列预算引用，事务内明确迁移/保留归档引用，不能把上月扣额隐式转到新账本 |
| 来源余额在确认前变化 | 以事务内最新值校验，整批失败并刷新，不仅依赖表单校验 |

退款作为可选的明确业务子类型关联原支出，不把普通收入当退款。使用正数退款额与原支出外键，累计不超原支出；消费报表单列毛支出、退款与净支出，正常收入与退款分开。退款流水按实际退款日期展示，预算释放指向原消费占用的原期桶；跨期报表需注明这种差异。删除原支出前处理退款依赖。若净分类金额出现负值，改用表格/条形图，不绘制无意义负占比饼图。

## 五、工程架构与模块边界

### 5.1 技术基线

- Expo稳定SDK、React Native、TypeScript；按所选SDK固定依赖及锁文件，使用Development Build验证Android。
- Expo Router负责模块页与详情路由；根抽屉使用与SDK兼容的导航组件，统一入口与返回行为。
- 服务端采用Node.js 22、TypeScript、Fastify与pg连接池；PostgreSQL负责事实数据、事务、索引与迁移。手机只持久化草稿/缓存。
- Zustand或轻量状态容器保存抽屉、当前账本、筛选和表单状态；业务金额不以界面缓存为事实来源。
- React Hook Form与Zod或等价方案负责静态与动态表单验证；所有规则仍在服务层复核。
- SVG图表验证折线、饼图、条形和列表；结果来自授权API。手机通过系统选择与分享保存下载的导出文件。
- XLSX库在Node.js服务端验证公式、内存和许可证；由PG一致性快照生成，手机下载；验证取消、鉴权及过期清理。

## 六、数据库迁移与一致性设计

### 6.1 逻辑实施顺序

下表为完整功能的逻辑分组，不是已部署SQL文件清单。当前服务器基础已按`server/db/migrations/001～006`落实，新增功能和修复从007起追加；实际版本及边界以部署记录为准。

| 迁移组 | 表或能力 | 必须具备的验证 |
| --- | --- | --- |
| 001 基础 | schema_migrations、entities、tree_nodes、settings、audit、drafts | 根唯一、父链、稳定ID、初始化不造业务数据 |
| 002 账本 | 分组、账本、主分类、transactions、remarks | 父子类型、账本方向、金额分、备注唯一 |
| 003 计划与存钱 | 目标、计划、来源分配、退款关联 | 实际引用唯一、分配上限、非负与退款额度 |
| 004 用户配置 | 辅助标签及绑定、字段定义/值/选项、关系定义/边 | 作用域、类型、字段迁移、基数约束 |
| 005 模板预算 | 系统/个人模板、实例、实体映射、方案、项、修订、预算桶 | 同账本同月单一有效方案、桶不重叠、金额闭合 |
| 006 扣额 | 操作批次、预算转移、反向事件、使用投影及重建元数据 | 事件双边一致、幂等唯一、投影可重建 |
| 007 查询与数据管理 | 查询索引、删除批次、导出/恢复日志、备份元数据 | 深树查询、删除祖先过滤、恢复阶段可回退 |

迁移编号是开发顺序，不承诺每组必须只有一个SQL文件。首次发布前可以有多次开发schema；已发布迁移只追加修复，不能改旧脚本后期待所有设备自动一致。

### 6.2 补充的业务记录

- `budget_usage_links`：交易ID、方案ID、互斥预算桶ID、占用金额、用途、来源修订；用于储蓄显式关联和可追溯映射。消费投影按交易与唯一桶生成，不能多写一条再扣一次。
- `budget_transfer_operations`：操作ID、请求摘要、账本/预算期、状态、时间；防止重复提交，不以按钮禁用代替幂等。
- `budget_transfers`：来源桶、目标桶、正数分金额、操作批次、撤销所指事件ID、前后快照；已提交事件不可直接覆盖。
- `transaction_refund_links`：退款流水与原支出关联，原支出剩余可退金额在事务内校验。
- `deletion_batches`：根删除操作、全部受影响实体与原位置，用于成组恢复和冲突展示。

金额快照用于解释历史，当前余额由有效事实重算；缓存不能独自变成钱包。预算转移端点必须由数据库外键指向存在的同方案桶，不能只存展示名。

### 6.3 写入事务标准

```text
解析与基础校验
→ 进入受控写事务
→ 检查幂等键、读取最新修订和余额
→ 校验树/字段/关系/预算/存钱的相关约束
→ 写业务表、关系、投影与审计
→ 提交
→ 使相关查询失效并刷新页面
```

跨多个来源的扣额只能整体成功或整体回滚。服务端按工作区行锁协调写入，金额操作统一锁顺序，忙碌/死锁/序列化冲突有限重试；不能重试具有未知结果的入账而不查操作ID。导出使用PG REPEATABLE READ一致性快照；恢复在隔离数据库验证，切换期间控制新的业务写入。

### 8.2 固定综合验收数据

1. 空白工作区、两个支出账本、一个存钱账本和至少12层分类，至少一个分类同时有直属明细和子分类。
2. 交通初始800、消费900，娱乐500，从娱乐扣100后分别0与400；真实消费900、总余额400。
3. 交通−100，来源A只有60、来源B有50，选择60与40，双方均不负；重复提交金额不变。
4. 补足后把原900消费改成850，交通余额50、娱乐400，总余额450，原扣额历史存在。
5. 同一100元明细同时有旅行/报销标签，任一查询只算100，分组条形可各100并标重叠。
6. 未配置预算也能记账；工资空值与显式0额度区分；新增未纳入分类的消费单列不漏账。
7. 同一交易恢复与计划重新执行冲突、多笔存钱超过来源、退款超过原额均被正确处理。
8. 字段改名/类型转换失败/归档选项/关系基数收紧、树移动后预算引用仍可解释。
9. 备份恢复与升级后，上述金额、路径、关系和历史一致，笔记入口仍禁用。

### 8.3 性能与兼容

使用固定中端Android真机和发布构建，记录型号、系统、内存、SDK与版本。规模基准为30账本、50,000实际明细、100字段、300标签及深树；另测大批字段值和扣额记录的实际关联量，不能只造空字段定义。

常用列表首屏目标约500毫秒、常用汇总约1秒，复杂跨树查询分页并显示进度。Excel大数据基准至少验证10,000条含字段明细，50,000条作为压力场景实测内存；若设备不能一次导出，应在导出前提供按月份/文件拆分方案，不静默截断数据。拆分不影响数据库完整性。

最低Android版本按选定Expo SDK确定并记录；至少覆盖最低支持版本和一个常见较新版本的文件分享、系统返回、升级和断网草稿流程。完成检查后，只有新变更或失败才重复相关测试。
